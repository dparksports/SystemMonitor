# AutoCommand III — v2026.10.31

Shields Up moves in: the standalone admin console's four rituals — take the
junk out, set the firewall, close the doors, silence the phone-home — are now
a tab inside AutoCommand, driven by the same engine set, with the firewall
baseline re-captured atomically every time a preset applies.

## What changed

- **🔒 The Shields Up tab (CONTAIN).** Quick Scan is the whole ritual as one
  checklist: it reads your machine's current state first, shows what is
  already done in green, and finishes the rest in order behind one master
  confirmation — with every result re-verified against live state instead of
  trusted. Below it, the four sections: **doors** (SSTP VPN service +
  miniports, the Wi-Fi Direct ghost hotspot, kernel debug, the Windows VPN
  service family, WAN miniports), **firewall presets**, **telemetry
  opt-outs**, **bloatware**, and the **OS-hardening switches** (IPv6, LSA
  Protection, UAC strictness, hosts-file audit). Every action asks first; No
  is the default button; almost everything reverses.
- **One data home.** The tab points its state at `%PROGRAMDATA%\AutoCommand`,
  where the file names already matched by design — `firewall_config.json`
  becomes the one desired-state store the drift enforcer and the tab both
  read. If the standalone Shields Up app left state behind, the tab offers to
  import it (your edited bloatware list, the telemetry revert history, the
  update-freeze ledger); a running standalone app gets flagged before the two
  can fight over the same switches.
- **The WSL footgun is fixed at the source.** The 2026-10-30 field report
  caught a Shields-Up-era mass-disable whose narrow whitelist silently took
  WSL2/Hyper-V egress down below the rule model. The widened whitelist (mDNS,
  Core Networking + the VM-infrastructure groups: icsvc, WSL, Hyper-V, HNS,
  wslservice, vmcompute) now lives once, upstream, in the firewall engine —
  both C# copies delegate to it — and the checklist pins it offline.
- **Presets apply atomically.** Applying a preset pauses the drift enforcer,
  applies, and re-captures the firewall baseline in the same operation, so
  Auto-Mitigate protects the preset's intent instead of endlessly
  re-disabling rules Windows re-enables (the frozen-baseline footgun from the
  same report). The Shield Up whitelist spares VM networking.
- **Be My Guest learns the shields.** Read-only `get_shieldsup_status` (every
  door, hardening switch, hosts audit and per-vendor telemetry state), plus
  three gated tools: `close_shieldsup_door`, `opt_out_telemetry` and
  `apply_shieldsup_preset` — each confirmed in AutoCommand, each reversible,
  and deliberately no door-enable path over the bridge: reopening a door
  stays a human decision made in the tab. The offline proxy stub list ships
  the new tools so clients see them before a session starts.
- **Same engine, both faces.** The door/privacy/hardening checks were
  extracted from the WinUI pages into pure services that the tab drives —
  the standalone app and the tab cannot drift apart, and the standalone app
  keeps working for anyone who prefers it separate.
- **Self-test coverage.** A new strict `HardenSelfTest` suite (in CI from this
  release) pins the data-root seam, the shared-file reload-merge-write
  behavior, the import copy/merge/idempotency rules, the quick-scan shape and
  the widened whitelist — all offline against a temp data root.

## Notes

- `Agent.Core`, `AgentHost` and `ProxyInstallSelfTest` now target the same
  `net10.0-windows10.0.19041.0` floor the app and AgentProxy already carry —
  the vendored Shields Up core needs a Windows 10 SDK surface for the WinRT
  package manager. No supported-OS change: the app's floor was 19041 already.
- The archived `dparksports/autocommand-windows` README mirror updates as
  usual; the standalone Shields Up README now points here.

# AutoCommand III — v2026.10.30.30

Layer 3 arrives in Traffic Peek: **🛡 Intercept this process** — the one honest
way to see what a program that can never write TLS keys (Windows services
included) actually sends.

## What changed

- **🛡 Intercept this process.** On any "encrypted (no keys)" flow in a
  program or tracked-service peek, one button starts a 15-minute intercept
  session: a local TLS-terminating proxy becomes the temporary system proxy
  (WinHTTP for services, WinINET for apps), the target's QUIC is blocked so
  it falls back to TCP, and only connections attributed to that exact PID are
  decrypted. Everything else is tunnelled through untouched. This is the
  plaintext path for schannel components — the wuauserv/Delivery-Optimization
  case the metadata view could never answer.
- **Visible and reversible.** An amber banner shows the session, its countdown
  and a ⏹ Stop now button; stopping (or closing the window, or the app, or the
  15-minute box) restores the proxy, removes the firewall rule and untrusts
  the CA. Every change is journaled before it is made — a crash mid-session is
  undone at the next app start. A corrupt journal is never guessed at.
- **Scoped trust.** The temporary CA is trusted machine-wide only while the
  session runs and removed by thumbprint at its end; certmgr shows it as
  "AutoCommand Intercept CA" whenever it is trusted. Certificate-pinned apps
  fail loudly during a session and are recorded as "refused intercept
  (pinning)" — a signal, not an error.
- **The rows land in the same peek.** Intercepted conversations appear in the
  flow list tagged "decrypted · intercept", with request/response bodies
  readable in place (text + hex) and exportable with 💾 Save bodies — in
  memory until you say so.
- **Self-test coverage.** A new strict `InterceptSelfTest` CI suite drives the
  journal round-trip, crash recovery (including the never-guess corrupt case)
  and the CA/leaf minting with DNS and IP SANs — all in a temp dir; the
  netsh/registry hooks themselves stay on the manual E2E pass.

# AutoCommand III — v2026.10.30.29

Python environments can now be instrumented: spawn call stacks and TLS
session keys, surfaced in the scoped peek for exactly the process you're
looking at.

## What changed

- **🐍 Instrument…** Every Traffic Peek window gains the per-environment
  opt-in dialog (recreated from autocommand-ii): environments are discovered
  from the registry, PATH, Store, conda, uv, pyenv-win, scoop/choco, a bounded
  deep scan for venvs, and python binaries this machine has actually run
  (replayed from the Sysmon archive — nothing keeps watching). Instrumenting
  writes two small files into that environment's site-packages — nothing else
  changes, and removal is one click in the same dialog.
- **Python audit trace.** A program-scoped peek of a python process now shows
  that process's audit-hook records: the spawn APIs it called, their arguments,
  and the full python call stack at the moment each fired — the "why", scoped
  to the subject instead of a standing tab.
- **TLS keys land in the same peek.** Instrumented pythons log session keys to
  the same keylog the peek already tails, so their HTTPS traffic decrypts in
  the flows list — alongside the call stacks that explain it.
- **Payload seam fixed.** The hook payload is embedded in the same assembly
  that reads it (`AutoCommand.Forensics.Core`) — autocommand-ii carried a
  latent bug where the installer would have failed at runtime because the
  resource lived in the app exe.
- **Self-test coverage.** A new strict `PyTraceSelfTest` CI suite drives the
  installer round-trip, environment detection (incl. embedded-distribution
  refusal), the bounded venv scan, the reader's offset-resume tail, and the
  payload embed; `docs\selftest\run-selftest.ps1` revives the end-to-end
  harness: real python, real TLS session, decrypted via the hook's keylog.

# AutoCommand III — v2026.10.30.28

Traffic Peek learns your subject: peer into a program instance, or pin a
service by name and let the window follow it across restarts.

## What changed

- **Three scopes, one peek.** The context menu now offers **Peer into this
  program (PID N)** — flows attributed to that instance via Sysmon — alongside
  the existing per-IP peek. One window per subject; a second request focuses
  the existing one.
- **⭐ Track this service.** On a svchost row, pin the hosted service by NAME
  (DiagTrack, CryptSvc…). A PID pin goes stale the moment the service
  restarts — the name doesn't. A tracked peek follows whichever svchost
  instance hosts the pinned service next, with zero user action on respawn.
- **🚀 Launch under watch…** Every peek window can start a program with
  SSLKEYLOGFILE set in its environment only, and opens a program-scoped peek
  for the new instance immediately — its TLS traffic decrypts as it connects
  (Chromium/Electron, curl, git, OpenSSL- and Python-based tools honor it).
  The key path is the recreated `AutoCommand.Intercept.Core` service
  (`TransmissionKeyService`), strictly local, per-program by default.
- **The coverage note.** On every "encrypted (no keys)" flow the window now
  says exactly how plaintext becomes possible and why it never will for
  schannel system components — instead of leaving an empty pane to interpret.
- **Engine.** `FlowDossierService` takes a scope (`remote ip` / `program` /
  `service`), with shared-host protection: a scope on svchost.exe is matched
  only by its exact PID, never by image. The offline NetWatch suite drives all
  three scopes end-to-end (16 new checks), including the restart-follows
  service case and the shared-host guard.

# AutoCommand III — v2026.10.30.27

Process Monitor learns to look inside a connection: right-click → **Peer into this connection**.

## What changed

- **Traffic Peek window (Process Monitor context menu).** Any connection row can now
  be peered into, scoped to its remote IP. While the window is open, AutoCommand
  reassembles the TCP conversations to that IP and shows every finalized flow with
  what it actually carried — and nothing is captured once the window closes. One
  peek per IP; nothing is written to disk; capture, decryption and event reads are
  all local.
- **Honest TLS verdicts.** TLS metadata (server name, ALPN, cipher, version) is
  always extracted from the handshake. Decrypted plaintext appears only when session
  keys exist — and the window says exactly why when they don't: Windows services
  (wuauserv, BITS, DoSvc) never expose keys, so their rows stay metadata-only by
  design instead of showing empty content.
- **Service activity pane.** For the same time window, the window lists what the
  hosting service logged — Windows Update, BITS and Delivery Optimization operational
  events — the plaintext answer for connections whose TLS can never be decrypted.
- **Session-key logging toggle.** The keylog opt-out (previously a flag file) is now
  one button in the peek window: disabling deletes the keylog and stops recording
  keys; the dossier never recreates a file you turned off.
- **Self-test coverage.** The NetWatch suite now drives the whole peek pipeline
  offline: synthetic TLS/plain flows through the reassembler, remote-IP scoping,
  PID attribution, the no-keys honesty path, and the capture refcount lifecycle.

(For context: the dormant Transmissions engines from the pytrace era are what power
this — same reassembler, same TLS decryptor, now reachable from a row you're
actually curious about.)

# AutoCommand III — v2026.10.30.26

The rain pane's width stops churning the list.

## What changed

- **Auto-fit width changes are debounced.** The alive-process count
  churns as connections start and stop, and every pane-width change
  re-measures the list's DataGrid — an un-debounced fit re-measures the
  grid at churn rate, which shows up as a busy cursor and a pane that
  never settles (worst right after folding the nav, when everything
  re-measures at once). The fit now applies immediately once, then
  settles on a one-second trailing cadence while the count keeps
  moving — the pane still tracks reality, the grid re-measures at most
  once a second, and a user-dragged (manual) width is unaffected.
- (For context: the invisible fold triangles and the missing drag
  resize were fixed in .25 — solid drawn arrows + a real splitter with
  double-click re-fit. If you're seeing a clipped rain sliver at the
  right edge, you're on .24; update.)

# AutoCommand III — v2026.10.30.25

The divider you can see, grab, and drag.

## What changed

- **The fold triangles are drawn, not typed.** The ‹ › characters were
  guillemets — a few pixels of ink at font size, in a gray a shade off
  the pane background, on a rail the same color as the panes beside it:
  effectively invisible, twice reported. The rail is now drawn with Path
  geometry (11×13 px solid triangles in the near-white primary text
  color) on a splitter strip in the border gray — visibly a control, in
  both themes. Verified by rendering the exact rail strip to a bitmap in
  isolation (a screen capture of the live app proved flaky).
- **The divider is a real GridSplitter.** Drag it anywhere between the
  triangles to give either pane more or less room; a size preview
  follows the drag. Double-click re-fits the rain pane to its alive
  columns (the auto-fit that sizes the pane to exactly its rain, no gap
  strip). Dragging marks the width as manual — the auto-fit stands down
  until the next double-click — and the chosen width persists in
  `%LOCALAPPDATA%\AutoCommand\rain_panel.txt` (`auto` / `manual=N`,
  old one-line files still migrate). The splitter disables in list-only
  mode (nothing to drag into a hidden pane) and the fold triangles keep
  their same corners.
- The rain pane's fold/restore behavior is unchanged: a hidden pane
  costs no frames, and the renderer still publishes the alive column
  count that drives the auto-fit.

# AutoCommand III — v2026.10.30.21

The rain's column count is the truth: one column per alive process,
never ten or more.

## What changed

- **Columns == alive processes.** Every snapshot counts the tracked
  processes that still have at least one live conversation row (the same
  rows the Process Monitor shows), and the pane lays out exactly that
  many columns — an IP leaves the table, its column leaves the pane;
  a new one arrives, a column slides out of the docked edge. `maxColumns`
  drops from 64 to **9** and is clamped 1–9 on load, so ten or more can
  never render regardless of what a hand-edited config says.
- **The cinema wall spans exactly the data columns** — hugging the docked
  edge — and the rest of the pane stays dark. Nothing alive, nothing
  rains. Streams persist across alive-count changes instead of being
  recreated, and any wall left outside the active region decays through
  the normal fade.
- **True edge anchoring fixed on the way**: the ranking promise ("busiest
  at the docked edge") silently broke whenever the grid wasn't full —
  `maxSlots-1-idx` clustered columns at the pane's left when docked
  right. Slots are now `gridCols-1-idx`, so the busiest column really is
  the rightmost (or leftmost, docked left).
- A column that loses its slot (death or cap) has its strip cleared once;
  the harness proves the shape: 3 synthetic PIDs → exactly 3 wall+data
  columns at the edge, everything else dark.

# AutoCommand III — v2026.10.30.18

The Audit tab renders, grant scope tightens everywhere, and 1,300 lines of
dead code leave the building.

## Fixed

- **The Audit tab actually renders.** v2026.10.30.15 shipped it with its
  incident rows blank and every severity badge stuck green: the bound
  members (`Severity`, `Sentence`, `Meta`, …) were public *fields*, and WPF
  bindings to fields silently produce nothing — the same 49-instance bug
  class the Blocks tab's redesign shipped with. The display members are
  properties now; grouping state that only code touches stays fields.
- **"Always allow" is now per-target for every mutating tool.** The shared
  bridge engine's grant key previously scoped per-tool except for the gate
  pair; since AutoScope's mutating tools run on this same engine, a
  session-wide "always allow kill_process" would have covered *any*
  process. Grant keys now carry the target (`ip` / `pid` / `task_path`) for
  every tool that has one — a grant covers exactly what the user saw in
  the confirmation, nothing more.

## Removed (dead-module scan across the family)

- `DefenderMonitoringService` and `DefenderPrivacyService` — compiled into
  every build, instantiated by no app.
- `ExternalStartMonitor`, `VendorCatalog`, `BloatwareStateConverter` —
  same story, whole files.
- `AuthenticodeVerifier` (this repo's copy — Shields Up ships and uses its
  own), four XAML-orphan converters (`StatusToColor`,
  `TaskStateToColor`, `AppNameToDisplay`, `GroupExpandedState`), and the
  `NetworkAdapterItem` / `EfiFileResult` / `NetworkConnectionItem` model
  classes (Shields Up carries its own live copies).
- Net −1,326 lines. The scan covered 441 types across the three apps,
  cross-checked against XAML and every repo before deletion.

## Upgrade notes

Restart the app as usual. No data, config, or session changes; block
inventories and audit trails are untouched.

# AutoCommand III — v2026.10.30.16

The Rain tab works when you come back to it — and tells the truth while
it's warming up.

## What changed

- **Rain tab fixed: returning to the tab resurrected nothing.** The first
  build attached fine, but WPF's TabControl tears a tab's content out of
  the visual tree the moment you select another tab (Unloaded — the
  renderer stops, correctly, so a hidden tab costs nothing) and reconnects
  it when you return. On that return, `IsVisibleChanged` fires while the
  view is not yet "loaded", the restart path declines — and then the
  attach guard saw the renderer already existed and early-returned. The
  rain was a black pane with a frozen `attaching...` strip for the rest of
  the session. Attach now re-applies visibility on every re-entry: same
  renderer, resumed drawing. Proven in RainSelfTest with an
  away-and-back round trip whose lifecycle log shows the draw counter
  freeze while away and continue from the same value on return
  (536 → 609 → 914 → ...) — pre-fix it stayed frozen forever.
- **The diagnostics strip can no longer starve.** Both the strip timer and
  the harness's ran at DispatcherPriority.Background — on a busy machine
  Background work can be starved indefinitely while the app itself stays
  responsive, so the strip froze mid-sentence (even at the stock
  `attaching...`) while the rain was fine, and lied about the state. Both
  timers now run at Render priority: two string writes per 500 ms are
  nothing, and the strip now tells the truth.
- **RainSelfTest grew a real regression harness**: the away/back round
  trip is scripted, every diagnostics tick appends a timestamped lifecycle
  line (cols / draws / fps / visibility / loaded / tree membership) to
  `%TEMP%\rainselftest.log`, and dispatcher exceptions land in the same
  log instead of dying silently.

# AutoCommand III — v2026.10.30.15

The gate tools work again, every change to your blocks becomes answerable,
and updating Windows stops being a panic-button decision.

## The gate crash — fixed

**`open_gate` / `close_gate` failed on every call** with WPF's "The calling
thread cannot access this object because a different thread owns it" — even
`dry_run`, which was supposed to touch nothing. Root cause: the bridge's UI
availability pre-check read `Application.MainWindow` (a thread-verified WPF
property) on the RPC listener thread, *before* the tool handler ran, so the
exception fired before the dry-run branch could ever be reached.

Three fixes, each regression-tested in BridgeSelfTest section 7 (whose stub
UI throws the exact field exception):

- **`IsUiAvailable` is thread-safe** — the `MainWindow` read is marshalled
  to the UI dispatcher; a shut-down dispatcher reads as "no UI".
- **`dry_run=true` bypasses confirmation at the engine level** — the
  documented "resolve and preview only" contract now holds even in a
  session with no UI at all.
- **A UI hook that throws denies cleanly** — clients get the actionable
  "no UI to confirm with" denial instead of raw WPF exception text.

## 🧾 Audit — a new CONTAIN tab

Every change to your blocks — yours, AutoCommand's, or anything else —
narrated in plain language, one incident per event burst, newest day first.
The status strip answers "does anything need me?" before the list appears;
red is reserved for external changes that were not confirmed undone.

- **Incidents, not log lines**: the monitor's 3-block burst reads as
  "AutoCommand blocked 2 addresses and 1 program over a quick burst"; a
  restore-guide pause reads as "The restore guide paused 162 blocks".
- **Fleet operations are now audited** — the panic button, Re-enable all,
  restore-except-risky, legacy consolidation, and manual rule toggles in

# AutoCommand III — v2026.10.30.4

**Block gates** for AI agents: a time-boxed unblock the user confirms for

## The agent flow

Three new MCP tools:

- **`open_gate(target, minutes, reason?, dry_run?)`** — temporarily stop
  blocking ONE specific blocked IP or process image for **1, 10, 30 or 60
  minutes** (the agent picks the shortest window its task needs). The user
  confirms the exact target in AutoCommand — the dialog shows the target,
  the rule count, the wall-clock auto-close time, and the agent's reason.
  Blocking returns ON automatically when the window ends. `dry_run` previews
  the resolution without asking anyone.
- **`close_gate(target)`** — close early, blocking back ON immediately.
  The tool descriptions teach this as good citizenship: every minute a gate
  is open is a minute its target is unblocked.
- **`list_gates()`** — what's open, remaining minutes, requester, reason —
  check before requesting; `list_blocks` rows now carry
  `gate_minutes_remaining` too.

**Specificity is enforced, not requested**: an ambiguous name (40 blocked
svchost targets) returns the candidate list with an error telling the agent
to be precise — it never acts. Unknown targets and invalid durations return
teaching errors. Re-opening an existing gate extends it after a fresh
confirmation; gates confirm every time (the "always for this session" grant
does not apply to them).

## Safety properties

- **gates.json is written synchronously before blocking turns off** — the
  one store that does not ride the managed write buffers, because a lost
  gate record would mean protection stays down.
- **App exit closes every open gate** (a dead app never leaves a door
  open); startup closes anything that expired while it was down, and the
  10-second `gate-watch` instrument (calibratable like every instrument)
  closes gates as their windows end.
- Only `AC-BLOCK-*` rules AutoCommand itself created are ever touched;
  every transition lands in `blocks-events.log` (`mcp`, `gate-expiry`,
  `gate-exit`), and the Blocks tab shows live gate state on the row
  ("gate 8m · mcp") with the auto-close time on hover.

# AutoCommand III — v2026.10.30.3

## Instrumentation Metronome — spread, calibrated, self-budgeting

- **One registry, one scheduler** for periodic work. Instruments are

  instrument — on/off, cadence (1 s → 60 s → Off), live last-run stats,
  restore defaults. Persisted to `cadence_settings.json`, hot-applied;
  `check_interval.txt` migrates once as the enforcer's calibration.
- **Self-budgeting**: a run over 500 ms on your machine auto-slows its
  instrument (×5, capped 30 s) with an amber note, instead of stuttering
  the desktop.
- Migrated: the security enforcer fast checks and the svchost trace poll —
  whose 1 s WMI enumeration now gathers **off the UI thread** (the UI
  thread never blocks on WMI), drops its every-5th-tick second WMI pass,
  updates status at 1/5th cadence, and caps its recording buffers.

## Managed disk writes

- **BufferedAppender** (Engines.Core): journal lines buffer per path
  (self-flush at 256 KB); state/store rewrites are last-write-wins with a
  content guard — identical content never touches the disk.
- Routed writers: the Sysmon archive (event lines *and* the watermark that
  used to fully rewrite per event), the agent bridge's activity/feed logs,
  and the blocks store (`blocks.txt` + `blocks-events.log`).
- Flushes ride the metronome (disk-flush instrument, 30 s default, user
  calibratable) plus app exit; **readers flush their own paths first**, so
  read-after-write stays exact. Crash window = one flush interval — safe by
  design: the blocks store reconciles from the firewall rules, the archive
  watermark tolerates boundary duplicates.
- Settings shows the receipts: flushed/buffered bytes with top sinks, a
  **Minimize disk writes** preset (5-minute flush, 1 MB buffers), and

# AutoCommand II v2026.10.27.7 — verify_block_containment: proof that blocks are silent

Blocking a process or IP has always shown you the attempts (the live
who-is-being-blocked feed). What it could not show was whether anything
was actually getting THROUGH. This release closes that loop.

## What is new in this build

- **`verify_block_containment`** (AI bridge tool): one call that proves a
  blocked process is silent, not just still trying. A block hit is a
  connect ATTEMPT — the kernel drops it and nothing logs the outcome — so
  no single source proves silence. This tool joins three: Sysmon-attributed
  attempts, the live kernel socket table, and the TLS-transmissions archive
  since the block was created. Per process instance it returns a verdict:
  - **contained** — attempts only; the block is dropping everything.
  - **stale-flow** — a socket whose owning process predates the block:
    firewall rules never sever flows that were already established, so it
    may still be alive. Sever or restart.

    a blocked destination since the block. Escalate.
  Blocks nobody is hitting are listed as quiet. The honest limits are in
  the output: the archive only holds TLS flows over 10 KB, so
  sub-threshold/UDP/DNS traffic needs `trace_analyze`.
- The verdict logic is a pure engine (`BlockContainmentVerifier` in the
  Contain core) with the same identity rules the monitor enforces — a
  reused pid is flagged, never accused. 15 new offline self-test checks
  cover every verdict and guard (43 total in the Contain suite, all pass).

# AutoCommand v2026.10.25.3

## The AI bridge that heals itself — and starts itself

Two failure modes both looked like "MCP not working," and both are gone:

**App restarts no longer break the AI session.** The agent proxy and the in-app bridge each enforce MCP's initialize-before-request rule — but the client's handshake is consumed once, possibly hours before an app update or restart gives the bridge a fresh lifecycle. Every tool call then failed with "Server not initialized" forever, invisible to the client (its pipe to the proxy never broke). The proxy now tracks which bridge instance it has handshaked with (`pid:port:token` from `session.json`) and replays the client's handshake the moment that changes — plus one reactive retry if a bridge resets without a session-file change. Each replay announces `tools/list_changed`, so a restarted app's new tools appear immediately. A `session.json` whose process is gone (crash without cleanup) now reads as offline instead of timing out on every call.

**"Investigate my PC" works even when nothing is running.** Two opt-in checkboxes in Settings → AI access, each with its own one-time consent:

- **Start the session automatically whenever AutoCommand runs** — the consent you gave at the checkbox stands on every launch; read-only unless the mutating preference is separately on.
- **If AutoCommand isn't running, let my AI assistant launch it in the background** — when a tool call arrives with no live session and no app running, the proxy starts AutoCommand headless: no window, **read-only**, exits by itself after 30 minutes. Windows shows one UAC approval (the app manages the firewall, so it runs elevated). A 5-minute cooldown prevents prompt storms; an already-running app is never spawned over — its session being off stays a Settings action.

Safety unchanged: loopback-only, per-session random token, token file deleted the instant the app exits, mutating actions still gated by their own preference and a per-action confirmation dialog — which a headless session can never show, so background sessions are read-only by construction.

Also in this release: the bridge feed now records `session_stopped` (making tonight's class of diagnosis a one-liner), headless mode exits silently when the interactive app is already running instead of starting a second bridge, and the offline tool guidance points at the new checkboxes so the first run teaches the fix.

# AutoCommand v2026.10.25.1

## One DNS resolver, one geo cache — ip-api.com trips collapse

AutoCommand was hitting ip-api.com far more than its answers justified. Not because caching was missing — a per-IP cache existed — but because of how it was used:

- **Four resolvers, four caches.** The Svchost monitor, Traffic Patterns and BITS each constructed their own `DnsResolutionService`: the same IP was resolved once per tab, and each instance kept its own 1400 ms throttle. Four throttles together ran at 4× the free-tier limit (45 req/min), so ip-api answered with rate-limit failures.
- **The shared cache file was being clobbered.** All instances persisted to the same `dns_cache.json`, each writing only its own in-memory dict — last writer wins. Every restart reloaded a gutted file, found everything "unresolved", and re-queried.
- **Failures were cached as facts.** A rate-limited or timed-out geo lookup stored the raw IP as the "hostname" for 24 hours: a wasted trip that also displayed wrong data, then repeated forever.
- **Per-IP keys missed the block.** org/country is constant across an operator's whole address range, but DNS-rotating fleets (Azure, Google, Akamai) present hundreds of distinct addresses — each one its own API call.

**The fix, in layers:**

- **`DnsResolutionService` is now a singleton** (`Instance`) shared by every tab and watcher: one cache, one throttle, one file writer, one background worker. `Start()` is idempotent, and BITS no longer disposes the shared resolver when its tab stops.
- **Geo answers are cached by /24 prefix** (`150.171.27.0/24`), not per address — one answer serves an entire rotating fleet block for **14 days**, persisted in `geo_prefix_cache.json` across restarts. The PTR-hostname cache stays per-IP, since reverse DNS really is per-address.
- **Local answers never reach the API.** Locally classified ranges (Microsoft/Azure, Akamai, Gcore — the most frequent talkers on a Windows machine) are answered offline from the same range table the Blocks tab uses; RFC1918, loopback, link-local, CGNAT and multicast addresses never spend a call.
- **Transient failures back off instead of lying.** A rate limit or timeout caches nothing and doubles the inter-call delay (1.4 s → up to 5 min, reset on success); a definitive "no data" answer is negative-cached for 24 h. No more day-long wrong "unresolved" rows born from one busy minute.
- **Cache files survive crashes**: all three (`dns_cache.json`, `dns_forward_cache.json`, `geo_prefix_cache.json`) now write atomically (temp + replace), with a 60-second save timer backing the existing checkpoints.

Steady-state effect: locally-classified talkers cost zero trips, each new operator block costs one trip per two weeks, and the 4× throttle overrun is gone. One visible change: addresses in locally-classified ranges now show as `Microsoft/Azure` / `Akamai (MS CDN)` instead of ip-api's `Microsoft Corporation · US` — same knowledge, no trip.

Not included (available if the throttle ever still binds): batching queued lookups into ip-api's 100-IP POST endpoint.

# AutoCommand v2026.10.25

## Blocked by name, blocked everywhere it runs from

Windows Firewall enforces an application rule by **exact image path** — and binaries move. The motivating failure: msedgewebview2.exe was blocked at `EdgeWebView\Application\155.0.4283.60\`, the WebView2 runtime updated to `.62` and deleted the old folder, and the block went inert while the process kept transmitting. Worse, re-blocking hit a name-only duplicate check that answered "already blocked" and did nothing. This release makes a process-name block mean what it says.

- **One rule per install path.** The first path keeps the primary rule name (`AC-BLOCK-APP app.exe (Out)`); every additional location — the new version folder after an update, a second install root, a per-user copy — gets a deterministic sibling rule (`… · <8-hex path hash>`), so the name is blocked wherever it runs from.
- **"Already blocked" is now path-aware.** Blocking the same path refreshes provenance; blocking a moved binary adds the sibling rule. The dead-end is gone.
- **New `AppBlockCoverageService`** keeps coverage current with no user action: it watches Sysmon process-create events and extends coverage **the moment a blocked exe name first runs from an uncovered path** — at the spawn, before its first connection. A startup sweep covers processes that were already running; without Sysmon, the sweep and retire pass still run.
- **Retire pass.** Rules whose program file no longer exists are removed once a live sibling covers the target — never the last rule of a target, so an app mid-repair is never silently unblocked. Runs at startup and every 6 hours.
- **Safety by construction:** auto-extension only ever blocks *more* — a malware binary name-squatting a blocked exe in another folder gets blocked too — so no confirmation gate is needed.
- **Audit trail:** every extension and retirement is journaled to `app-block-extensions.jsonl` with trigger, parent image and rule name, and survives restarts.
- **Unblock and pause/resume now operate on the whole name** — all sibling path rules — not just the row that happened to be clicked.
- **Visibility:** the Blocks tab shows a 🕳 glyph on rules whose path is gone (tooltip explains and says what happens next); the `list_blocks` bridge tool reports a `stale_rules` count per target; the block-hit feed attributes connects by name too, so a hit from a not-yet-covered sibling path reads as an app-block hit, not an unexplained connection.

## Phone Home

New tab: one card per curated Windows talker (DiagTrack, CryptSvc, Delivery Optimization…) — what the service is, what it actually sends, and its current block state. The "which of Windows' own services is phoning home, and did I already block it" question answered on one screen.

## Traces

New tab: project-based tracing. A project is a file under `%LOCALAPPDATA%\AutoCommand\traces\projects` — hand-edits and dropped-in files are picked up by a watcher, and sharing a project means copying its file. Per-project application blocking with full provenance and metrics.

## Site Doctor: "the site is fine — its dependency is blocked here"

The tab formerly known as "Why is this site slow?" could not see one failure class at all: a site whose **own servers answer perfectly** while its sign-in or parts of its pages fail, because an address the *page depends on* (captcha, assets, APIs) is on this machine's own block list. It used to answer "Healthy — try a private window with extensions off", actively pointing away from the cause.

- **Why the old pipeline was blind:** a firewall-dropped connect dies before the TLS ClientHello, so it carries no hostname and never enters the transmissions archive — the probe measures the typed host only, and the block cross-check only looked at that host's failed edges. The only record of a blocked connect is the Sysmon EID 3 join against the block inventory.
- **New evidence pass** (`DependencyBlockService`): anchors on the archive's recorded page loads ("brave.exe fetched www.spectrum.net at 08:23"), pulls blocked connects from the same browser within ±2 minutes of each load, and attributes every blocked address by what it has **served on this machine** (recorded SNI history — "this address also serves mail.google.com").
- **New verdict, `DependencyBlocked`** — ranked above the remote-cause rules, red-panel, headline naming the browser, the blocked IP, what it serves and when: *"www.spectrum.net's own servers answer fine — but at 08:23, brave.exe made 7 blocked connection attempts toward 142.251.34.67 — an address this page depends on…"* The **one-click unblock** button now covers the dependency addresses too ("🚫 Unblock N address(es) this page depends on"), fully reversible from the Blocks tab.
- **Intermittency explained:** the page's dependency hosts are resolved live and crossed with the block list — "www.google.com currently resolves to 8 addresses; 2 of them are blocked here — that rotation is why it comes and goes."
- **Honesty guards:** a blocked connect is called causal only inside a recorded visit window; hits outside it surface as context and never hijack a Healthy verdict. Attribution never guesses past recorded history.
- **Signpost for users who don't know the tab is for them:** on load, a hint appears when a browser has hit blocked addresses in the last day — "Brave hit blocked addresses 4 time(s) in the last day — if a page or sign-in failed, that's usually why. Check the site."
- **The AI bridge gets the same answer:** `diagnose_site` runs the identical pass (its tool description no longer says "slow" only) and returns a `dependency_blocks` section — hits with process, attempts, timestamps, served-hosts and block provenance, plus the rotation facts.

## Rename: "Site Doctor"

A question-shaped header ("Why is this site slow?") self-selects for slowness — a user staring at an authentication error concludes the tab isn't about them and never opens it. The tab is now **🩺 Site Doctor**, with the scope stated where you type: *"Slow, failing, or can't sign in — one 60-second check that measures, compares and explains."*

## Self-test

New section 5b replays the login-failure shape end to end over synthetic fixtures (healthy probe edges + in-window blocked connects, the exact capture that motivated the feature): the join, attribution, block provenance, exclusions (other processes and other browsers), rotation math, the new verdict, and the honesty negatives (nearby-only hits keep `Healthy`; the join stands alone with no probe). 43 checks, all passing.

# v2026.10.21 — Why is this site slow?

A new WATCH tab that answers the question every monitoring app dodges:
**"this one site feels slow — is it me?"** Born from a real diagnosis on
this codebase's own development machine (a site whose refreshes stalled
for seconds while every other site was fine), it automates the method
that cracked that case — and fixes the honest-UX trap that nearly
produced a false verdict along the way.

## New: 🩺 Why is this site slow?

- **Type a site (or pick one from your recorded traffic) → Run 60-second
  check.** The check reads the Transmissions archive (edge dispersion,
  retry bursts, connection churn), sends a small strictly-capped set of
  connections — about 21 operations, every one listed in the log — and
  compares against a control site you actually use.
- **One plain-English verdict, one reversible next step, the math one
  click away.** Verdicts: Blocked · Local TLS stack (every handshake
  fails, controls included — a post-hardening condition observed in the
  wild) · Server drops some handshakes (the works-in-one-app signature)
  · Server roulette (short-TTL DNS steering) · Far-away servers · No
  network problem found — with an honest "fast now, but history shows
  bursts" split.
- **Dual-shape TLS probe**: each server address gets two handshakes —
  the Windows-default hello and a plain TLS 1.2 hello. A server that
  answers one and silently drops the other is exactly the "slow
  refresh" signature, and now it's measurable.
- **AI guests get the same tool**: read-only `diagnose_site` on the Be
  My Guest bridge runs the whole pipeline in ~30 seconds.

## Fixed: the Down column can no longer lie

The Transmissions archive recorded `server_bytes: 0` on every row for
every site — the capture socket was seeing outbound only (RCVALL_ON
depends on the NIC honoring promiscuous mode). It now requests
`SIO_RCVALL_IPLEVEL` first (both directions at the IP layer, no
promiscuous dependency), falls back on older stacks, tallies inbound
vs outbound per session, and when a session is one-way the tab says so
in a banner: a 0 in Down means "not observed", not "nothing came
back". This is the readout that nearly produced a false "replies are
blocked" verdict during the original diagnosis.

## For developers

`SiteDoctorSelfTest\` — all pass (one loud SKIP by design on machines
whose schannel cannot host TLS). Full subsystem write-up in
`docs/TECHNICAL_NOTES.md` → *Why is this site slow?*

## New: 🔴 Who is being blocked, live (Blocks tab + AI tools)

Blocks fire **silently**: Windows Firewall vetoes the connect at the
kernel (instant access-denied) and emits nothing the app can subscribe
to. Until now the Blocks tab's hit counts came from `pfirewall.log` —
which Windows ships **off by default** and which carries IPs but no
processes — so a block breaking someone's browsing (the
`accounts.google.com` case: "This site can't be reached" while every
other Google page worked) was invisible exactly when users needed it.

- **Live feed with process attribution**: every Sysmon EID 3 connect
  attempt is joined against the blocked-target inventory (30s refresh)
  — process, PID, blocked destination, attempts, first/last seen — in
  a new "Recently blocked connects" grid that self-refreshes every 15s.
  Works out of the box, no firewall-log configuration needed; history
  persists across restarts (24h ring, JSONL beside the archive).
- **classify_ip now answers the real question**: range classification
  *and* whether the IP is on the explicit blocked list — rule count,
  since when — the part the range classifier alone could never see.
- **New AI-bridge tools**: `list_recent_block_hits` (the live feed),
  `list_blocks` (inventory + hit counts), and `check_host` — the
  one-call "why can't I reach this site?" triage that resolves the
  hostname, checks every address against the blocked list, and explains
  the DNS-rotation intermittency that makes per-IP blocks feel random.
- **pfirewall.log demoted to honest second source**: richer parsing
  (first/last seen + process paths), auto-enabled once at startup
  (never re-enabled if you turn it off), and the stale-leftover-file
  false-positive that could hide the enable button is fixed.

# AutoCommand v2026.10.20.6

Layer 3 for the Transmissions tab: an intercept for apps that can NEVER write
TLS session keys - Schannel-based Windows system components (svchost services,
taskhostw, conhost-hosted injected code), pinned or exotic clients. Until now
those rows ended at "encrypted (no keys)" with metadata only; this release
gives them a one-click, time-boxed, fully reversible decryption path.

## Why driverless, unlike the open-source interceptors

mitmproxy's local:<pid> capture and similar tools redirect traffic with
WinDivert - a kernel driver that on Windows 11 26H2 fights memory integrity
(HVCI), Smart App Control enforcement, and Microsoft's 2026 removal of
cross-signed-driver trust. AutoCommand takes the route that reaches exactly
the target set this feature exists for, because Windows services route
through WinHTTP: a local loopback proxy installed as the temporary system
proxy. No driver, no SAC exceptions, works everywhere.

## The intercept session (15 minutes, auto-reverting)

- Every accepted connection is attributed to its owning PID through the
  kernel TCP table. The TARGET pid's connections are decrypted - leaf
  certificate minted per hostname from a per-install "AutoCommand Intercept
  CA", upstream validated for real, both legs TLS, never a downgrade. Every
  other app's connections tunnel through byte-for-byte, untouched.
- The CA is trusted machine-wide only while the session runs, and removed at
  the end. The WinHTTP + WinINET proxy settings and the per-program UDP/443
  block rule (QUIC falls back to TCP/TLS) are journaled BEFORE installation;
  a crash leaves the journal, and the next app start undoes everything it
  describes. App exit also stops the session.
- Certificate-pinned clients fail loudly - recorded as "refused intercept
  (pinning)", which is itself a detection signal. Intercepted traffic lands
  in the same Transmissions grid, tagged "decrypted - intercept", with the
  full archive treatment: message decode, SHA-256, >10KB lens, body viewer.
- Strictly observe-only: bytes are teed and recorded, never modified in
  transit.

## UX

- Encrypted rows gain "Intercept this process..." with a consent dialog that
  states exactly what will happen and how it reverts. An amber banner counts
  down the session with a Stop-now button.
- The system-component restart-block message now points at the intercept
  instead of claiming metadata is the ceiling.

## Known limits (honest ones)

- Apps that ignore both WinHTTP and WinINET proxy settings (raw sockets)
  bypass the intercept - the WinDivert transparent route remains a possible
  future escape hatch for those, with the driver-signing caveats above.
- HTTP/2 bodies are detected and shown as raw bytes (no HPACK demux yet),
  same as the keylog path.

# AutoCommand v2026.10.20.4

Follow-up to v2026.10.20.2's Transmissions tab. That tab could show what apps

# AutoCommand v2026.10.20.2

New WATCH tab: Transmissions. Every TLS conversation this machine has with the
cloud becomes a readable row - what was sent, to whom, by which process - using
the SSL session keys that key-honoring apps can be asked to write. This is the
tab that answers "what exactly left my machine?" without guessing from byte
counts.

## The Transmissions tab (always visible, no opt-in)

- **Each finalized TLS flow becomes a row**: time, pid and process (Sysmon EID 3
  attribution), the SNI hostname, the destination, the RDAP provider behind the
  IP (Alibaba, Microsoft, Akamai, ...), wire and decrypted byte counts, and a
  status. Flows that decrypted say "decrypted"; the rest say exactly why not -
  "encrypted (no keys)" most commonly. Uploads above 10 KB wear an amber badge,
  and the grid defaults to that lens because bulk uploads are the exfiltration
  shape that matters.
- **Message-by-message content viewing**: decrypted directions are decoded into
  HTTP messages - chunked transfer, gzip, brotli and deflate bodies included -
  viewable as pretty (JSON pretty-printed, form fields URL-decoded), text, hex
  or headers, with a per-flow SHA-256 and a save-body button. HTTP/2 streams
  are detected and shown as raw bytes with an honest label rather than
  mis-rendered.
- **Nothing truncated, everything local**: rows archive to
  %LOCALAPPDATA%\AutoCommand\transmissions as a daily greppable JSONL index
  plus full-body blobs, 30-day retention with a 256 MB bodies budget. The
  SHA-256 per row keeps "what was sent" provable after the fact. Nothing leaves
  the machine: the AI bridge exposes metadata only (new read-only
  get_transmissions MCP tool), never bodies.

## Getting keys, two ways

- **System-wide key capture** (opt-in checkbox, confirm dialog): sets
  SSLKEYLOGFILE in the user environment pointing at AutoCommand's existing
  user-only-ACL, rotated keylog, and broadcasts the change so newly launched
  apps inherit it. Chromium/Electron browsers and apps, curl, git, wget,
  OpenSSL- and Python-based tools honor it from their next launch on.
  Schannel-based Windows components ignore it - their flows keep the truthful
  "encrypted (no keys)" status with full metadata. Turning it off wipes the
  key file.
- **Launch under watch**: pick one program; AutoCommand starts it with
  SSLKEYLOGFILE set in its environment only - the precise instrument for a
  single suspect app.

## Engineering notes

- The pipeline reuses the existing raw-socket TCP reassembler and TLS
  decryptor, and adds an all-process Sysmon connect watcher for pid
  attribution, a bounded background queue (drop-counted if capture ever
  outpaces decryption), and a 96 MB in-memory body cache with archive
  fallback for instant viewing.
- Recorder rule: watching starts on first open of the tab and deliberately
  survives tab switches; it stops on Stop Watch or app exit, where the
  pipeline drains what the capture's final flush finalized.

# AutoCommand v2026.10.19

The Blocks tab. A real block list told the story: 50 of 64 blocks labeled
"svchost.exe", 66% of them on Microsoft infrastructure, made in overnight
bursts — a list that could not answer its own questions. "What did I even
block?" "Which of these is breaking the thing that just stopped working?"

## The Blocks tab — blocks grouped by the service that made the connection

A new ⛔ Blocks tab in the CONTAIN group lists every AutoCommand firewall

"Defender Antivirus Engine" — never a wall of identical "svchost.exe"

blocked; orange degrade features. Rows show what was blocked, when, the

rules and lets traffic flow immediately, but deletes nothing — every
record stays in the list to re-enable, and every action lands in an
append-only history log.

## blocks.txt v3 — identity captured at block time

The block record format grows up. v3 rows carry the service identity,
display name, classification snapshot, origin, attribution source and
pause state — captured the moment the block is made, while the PID (and
its identity) still exists. The file moves to
`%LOCALAPPDATA%\AutoCommand\blocks.txt`: the old CWD-relative file was

version-tolerant — v2 rows and the older myfirewall 3-field rows (both

**Attribution repair recovers the past.** "🔎 Repair attribution"
back-fills identity for legacy rows in one pass: the 30-day Sysmon

## The Restore guide — "it broke; which rule do I lift?"

# AutoCommand v2026.10.18.1

A one-feature patch release for the Process Monitor's block flow: what
happens when you go to block a process and it has already run away. Short
version — it's blockable now, honestly, safely, and from the right identity.

## Blocking a suspect that already ran away

Processes you want to block have a habit of being gone by the time you decide
to. That used to be two bad outcomes: if the row had a Sysmon path the block
succeeded *silently* — you'd think you stopped something that had already
finished talking — and if it didn't, you got a dead-end "could not determine
process path" error. Both are gone. The block was never really about the live
process anyway: the firewall rule matches the exe's **path** and arms its next
run, so an exited suspect is fully blockable as long as the path can be
recovered. Now it always is:

- **The row's Sysmon capture** is the first source — it recorded the image
  path when the row was created, precisely so dead rows stay actionable.
- **The 30-day Sysmon archive** is the fallback when even that is missing:
  the suspect's create-event *is* its identity (path, command line, parent,
  hashes), and when several recycled PIDs share the number, the record that
  matches the row's start time and image wins.

And the flow is honest about what happened. The confirmation says so plainly
— "Process already exited — block its executable for next time?" — with the
limitation spelled out: the rule covers that path; a copy of the exe
elsewhere is not blocked. The success toast repeats it when the prompt was
suppressed, and the rule's Description carries an `exited` (or
`path-from-archive`) marker for wf.msc audits later. When nothing can be
recovered, the error is replaced by guidance: block the remote IP it talked
to, or open the PID inquiry for everything recorded about it.

One hazard fixed on the way: the old flow queried the live PID *first*, so a
recycled number handed the block to whatever unrelated process now owns it —
silently. Exited rows no longer consult the live PID at all, and live rows
cross-check the name first (the same guard the kill flow has); a mismatch
blocks the row's own process, not the PID's new tenant. The unblock path uses
the row's identity too, so unblocking can't target a recycled PID's path
either.

## Known deferred

Name/hash watch-rules (block the exe *wherever* it lands next, not just the
recovered path) and a `block_process` agent tool; the engines are untouched
and the offline self-tests still cover them.

Description carries a `confirm-suppressed` marker, auditable in wf.msc later.

Every per-block success MessageBox is gone. Blocks now report through a
small toast in the corner of the grid with a **↩ Undo** button, and it
auto-hides after a few seconds. The real confirmation is the row visibly
flipping to blocked in the list.

## Blocked vs allowed, at a glance

A new **Block** column leads the grid:

- **⛔** — this row's traffic is denied (an IP and/or process block rule is
  active).
- **⏸** — block rules exist but are disabled (the fleet pause) — traffic
  actually flows, so it's not shown as blocked.
- empty — allowed, which is the outbound default; unmarked means nothing to

The right-click menu tells the truth too: on a blocked row, "⛔ Block remote

# AutoCommand v2026.10.17.2

The two gaps named in v2026.10.17.1's "honest accounting," closed — plus the

## IPv6: the snapshot sees both families now

`TcpConnectionTable` enumerates `GetExtendedTcpTable` twice — AF_INET and
AF_INET6 (`MIB_TCP6ROW_OWNER_PID`) — so every sampled view (the MCP
`get_monitor_rows` snapshot, the Process Monitor startup seed, the Svchost
Trace baseline + 1s poll) sees established TCP in **both address families**.
IPv6 endpoints render as `[addr]:port`, netstat-style. A held `[::1]`
connection — invisible to the v2026.10.17.1 table, and, as it turned out, to
`netstat -ano -p tcp` itself on some builds — is now a first-class row, proven
live by the self-test.

- **One destination predicate, both families.** New shared
  `TcpConnectionTable.IsLocalOrNonRoutable`: loopback, link-local (fe80::/10),
  ULA (fc00::/7 — IPv6's RFC1918), multicast, broadcast. `IsIgnoredIp`
  delegates to it, which also fixes the **event path**: IPv6 EID 3
  destinations used to slip past a literal `"::1"` check and could seed
  link-local/ULA addresses as if they were internet rows.
- **Trace tab loopback filter made exact** — `Contains("::1")` also matched
  `fe80::1`; now `ip == "::1"` (the tab traces LAN traffic by design).
- `Classify` and the known-cloud CIDR list are IPv4 by construction; IPv6
  destinations classify as "IPv6/other" honestly rather than being silently
  matched. Extending the cloud catalog to v6 ranges is future work, noted
  below.

## Sysmon archive: weeks of history, readable on disk

The live channel is a rolling window (192 MB ≈ half a busy day). New
`SysmonArchiveService` makes "every spawn retroactively traceable" true for
weeks:

- **Backfill at every app start** — the entire retained channel is read and
  appended, skipping what's already archived via a (recordId, utc) watermark
  (record id alone lies when the log is cleared; time leads, id breaks exact
  ties). Cheap precheck: the channel's newest record vs the watermark.
- **Live append while the app runs** — an `EventLogWatcher` on the whole
  channel archives every event as it arrives. All EventData fields are
  preserved verbatim, so an archived EID 1 is a complete substitute for the
  live one: command line, parent image, hashes.
- **Storage is house-style JSONL** — one readable, greppable file per day
  under `%LOCALAPPDATA%\AutoCommand\sysmon-archive\`, pruned after 30 days
  (disclosed on the Sysmon Audit card, which now shows an Archive line:
  events, day files, retention).
- **Readers merged**: the PID Inquiry falls back to the archive when the live
  channel no longer holds a PID's spawns — the verdict that used to read
  "ancestry is unrecoverable" now produces evidence labeled *"Sysmon archive
  create-event (EID 1) — wrapped out of the live log."* The MCP `tail_sysmon`
  tool gains `archive=true` to query the archive instead of the live log.
- Unelevated sessions degrade silently: no channel access → no archive
  activity, nothing crashes, nothing is guessed. Events from before the
  archive's first backfill that already wrapped out of the channel are, by
  definition, gone.

## Process-name attribution: the netstat era ends

Root cause of the mislabel: the monitor snapshot joined a WMI PID→name table
against netstat output sampled at a different instant — a PID reused in
between inherits the previous owner's name.

- **One syscall instead of a child process.** New `TcpConnectionTable`
  (IP Helper `GetExtendedTcpTable`) returns every established IPv4 TCP row
  with its owning PID at a single kernel instant — no spawned netstat.exe,
  no text to parse, microseconds of skew. Every former call site uses it:
  the MCP `get_monitor_rows` snapshot, the Process Monitor's startup seed,
  and the Svchost Trace tab's baseline + 1s poll (which had been spawning
  netstat.exe once per second — the monitor no longer appears in its own
  process landscape). Runtime-validated against netstat output on the
  development machine: identical row sets, zero differences either direction.
- **(pid, start time) is the identity; a bare PID is not.** The name
  snapshot now carries `CreationDate` from WMI and stamps
  `process_started_utc` on every row — the same rule the PID Inquiry
  enforces against PID recycling.
- **Never guess a name.** A row whose owner exited between the kernel table
  and the name pass is labeled `attribution: exited` ("(exited during
  snapshot)") or `recovered-from-sysmon` — the image Sysmon recorded in the
  PID's most recent EID 1 create event, which PID reuse cannot corrupt. A
  PID whose name differs from the previous snapshot gets
  `pid_reused_since_last_snapshot: true` instead of a silent overwrite.
- **tail_sysmon printed `PID -1` on every line** — the property index read
  ProcessGuid (index 2) where ProcessId lives at index 3. Fixed.

Measured on the development box: ~15,000 events/hour during ordinary
dev/agent activity, and the whole 64 MB default channel held ~64k events —
roughly four hours of history. Overnight incidents wrap out before morning
triage (the motivating investigation found zero Sysmon evidence for exactly
this reason). Install, repair and the startup health pass now raise the
Operational channel to 192 MB (`EventLogConfiguration`, grown in place —
existing events are kept). Best-effort: without elevation the default
retention stands and nothing else changes.

# AutoCommand v2026.10.16.2

Second same-day follow-up to v2026.10.16. The Process Monitor gets the structural fix for "no traces of svchost", plus a leaner status bar.

## The Process Monitor now seeds existing connections at start

- **The trap.** The monitor is event-driven: a row appears only when Sysmon logs a *new* network connection (Event ID 3) after you press Start. svchost's dominant channels are long-lived — the WNS push channel dates from boot and rarely reconnects, Delivery Optimization only connects during update fetches — so minutes could pass with zero new svchost events while browsers constantly open fresh ones. # AutoCommand v2026.10.16

AI access (the Be My Guest tab) reliability release: the MCP server now starts in every client environment, upgrades cleanly with the app, and speaks the MCP protocol correctly. Honest accounting below — four real bugs fixed, two of them embarrassing.

## Bug fix: the proxy could not start inside desktop MCP clients

- **The trap.** Desktop MCP clients (Electron apps especially) routinely bundle their own .NET and export `DOTNET_ROOT` for everything they spawn — including copies older than .NET 10. A framework-dependent apphost honors that variable, never falls back to the machine-wide runtime, and exits **before any managed code runs**. The client just showed "server failed to start" with nothing actionable. (Reproduced with an empty `DOTNET_ROOT` and with a real .NET-8-only runtime: exit `-2147450749`, "You must install .NET to run this application".)
- **The fix.** The proxy now ships as a **self-contained single-file exe** (~15 MB, runtime bundled, IL-trimmed — `release.ps1` publishes it into the zip's `tools\AgentProxy\`). No framework lookup happens at all, so a hostile `DOTNET_ROOT` cannot break the spawn. Verified against an empty root and a genuine .NET-8-only vendored runtime.

## Bug fix: the deployed proxy never refreshed, and copy failures were swallowed

- The installer's "is the file set there?" check meant **any later release was silently skipped** — clients kept spawning a build from whenever they first registered, forever.
- When the copy did run and a file was locked by a running proxy, the code **silently registered a dev-tree path** as the client's spawn target — a folder that moves or gets cleaned.
- Now: installs go to `%LOCALAPPDATA%\AutoCommand\tools\v<version>\` — a fresh folder per app version (a running proxy never locks the copy, a version bump always refreshes), locked sources fall back to the newest previously-good install with a visible message instead of a dev path, stale folders are cleaned once unlocked, and the proxy's version follows the app's (`release.ps1` bumps both csprojs). Covered by a self-test (`dotnet run --project ProxyInstallSelfTest`) driving refresh, lock and fallback scenarios.

## Bug fix: MCP protocol conformance

- **Protocol version was blind-echoed** — ask for `1999-01-01` and we claimed it. Now negotiated against a supported set (2024-11-05, 2025-03-26, 2025-06-18), same rule in both halves.
- **Requests before `initialize` were answered** (a bare `tools/list` as the first message returned the tool list). Now refused with `-32002`, per the MCP lifecycle — in both halves.
- **`tools/list_changed` could beat the `initialize` response out the door** when a session flipped mid-connection. Now emitted after the in-flight response, and only for initialized clients.
- **Wrong error code**: a dead session answered `-32002` ("not initialized") — a lie, the client *had* initialized. Now `-32603` with the same human guidance, and forwarding failures **echo the request id** (they used to answer `id: null`, which strict clients drop).
- **Server identity** (`serverInfo`) is now identical offline and online, so client UIs stop relabeling the server when a session flips.
- **Registration preflights the install**: the Register button spawns the installed exe and requires an MCP handshake — once normally, once under a poisoned `DOTNET_ROOT` — before writing any client config. No more "registration succeeded, nothing works".

## Bug fix: successful tool calls answered `isError: null`

- Every successful `tools/call` returned `"isError": null` (a nullable flag serialized straight into the JSON-RPC envelope). The MCP schema requires a boolean when the field is present — strict clients (ZCode among them) rejected the whole response, so tools executed fine on this machine while the assistant saw a schema error. Now always a real `true`/`false`, with a regression check in the bridge smoke test.

## Also

- Proxy lifetimes (spawn parent, client name, stop reason) now land in `%LOCALAPPDATA%\AutoCommand\agent\activity.jsonl` next to sessions and tool calls, and a parent-PID watchdog plus stdin EOF make sure the proxy never outlives its client.
- `docs\TECHNICAL_NOTES.md` gained an "MCP server (AgentProxy)" section: two-half architecture, the `DOTNET_ROOT` trap, supported protocol versions, and the by-hand test recipes. `test-agent-proxy.ps1` was rewritten to publish the proxy exactly as shipped and cover negotiation, lifecycle, flip ordering, session restart, error codes and both poisoned-`DOTNET_ROOT` cases (30 checks).

# AutoCommand v2026.10.14.1

Same-day follow-up to v2026.10.14. Identical feature set plus the two changes below; the first same-day release under the calendar versioning scheme, hence the fourth `.1` segment.

## Every svchost instance is distinguishable by name

- **Process Monitor rows no longer say just `svchost.exe`.** All ~74 instances share one binary, so a row now resolves the instance's hosted service (SCM ground truth, `Win32_Service`) plus its command-line `-k`/`-s` tokens: `3784 (svchost.exe [WpnService])` — the `-s` service is the identity, `-k netsvcs` only the group pool. The full decode (`svchost.exe -k netsvcs -p -s WpnService`, corroboration verdict, service display names and states) is one hover away.
- **Hidden command lines are disclosed, not guessed.** A standard user's WMI cannot read SYSTEM svchost command lines (66 of 74 instances here) — the tooltip and PID Inquiry say so and suggest the elevated rerun instead of inventing a `-s` claim.
- **Masquerade signals surface in three places at once.** A `-s` claim that contradicts the SCM-resident services for the same PID, or a readable command line with no `-k` at all (the SCM always passes it), flags in the Process Monitor row, the Svchost Trace timeline and its analysis pane, and the CLI analyzer's new detector #6. Per-user services match their `template_LUID` instantiation (`-s CDPUserSvc` ↔ `CDPUserSvc_56ec2`), so genuine instances never false-flag. Verified against the synthetic-threat trace (6/6 detectors), planted edge cases (exactly the 2 planted flags), and live captures of all 74 instances (0 false flags).
- **Identity sticks to the tenant, not the PID.** Rows re-attributed after PID reuse re-resolve their service; svchost firewall blocks and the PID-inquiry dropdown carry the service name so provenance survives in `wf.msc` and reports.

## Task attribution keyed by Sysmon ProcessGuid

- Attribution for `taskhostw.exe` rows now prefers Sysmon's **ProcessGuid** (unique per boot, immune to PID recycling) over the PID wherever a create-event carries it, falling back to a start-time-guarded PID lookup (±5 s) when it doesn't. A **Sysmon EID 5 (process-terminate) watcher evicts the PID-keyed entry the moment the taskhostw exits**, live and in backfill — a later process inheriting a taskhostw's PID no longer inherits its scheduled task.
